最近古法编程写了个后端服务，这个后端服务的功能很简单，就是定时从一个数据源读取数据，然后将数据加工后存到自身数据库里，最后提供一系列接口给 Grafana Dashboard 展示数据。

在本次古法编程之前的几个月，我用 AI 写过一版，用的模型还是当时编程最强的 Claude Opus。我记得当时只用了半天时间就写完了，其中大部分时间还是在对接需求和修改 dashboard，只有十几分钟是在写代码。具体代码怎么实现的我也没看，反正 dashboard 展示都正常的，部署上去后我简单看了下 dashboard 没发现什么问题，也就没再关注了。

一段时间后，别的同事在看这个 dashboard 发现了些问题，有的是数据没处理干净，有的是要增加类型。感觉都是些小问题，我就翻出代码打算自己来修改了。不看不要紧，一看就发现不少让我觉得有点烦躁的代码。又翻了翻当初保留的设计文档。。。嘶，设计得也没毛病啊，怎么就写成这鬼样子了。

首先，大的设计是没什么问题的，毕竟功能简单，而且只是个内部服务，没什么好设计的。小的功能、方法也是没问题的，而且也用到了不少我都不知道的、更现代的写法。让我烦躁的点就在于，AI 从大的设计到小的方法之间的链路、项目结构、模块化设计等方面写得极为草台班子，像极了我刚学编程那会儿，只要功能正常，中间就糊弄过去的样子。

其中并发处理最让我无语。明明设计方案写得是并发处理，代码里面也做了并发，但我反复看了几遍后，发现 AI 加了一堆锁去保证并发安全和解决服务端限流问题，于是这几乎就变成了串行处理。难怪读取数据到写库至少有十几分钟延迟，亏我还以为是数据源的数据太多、sqlite写入太慢导致的。

尝试改了下代码，但没跑起来，我也不想再让 AI 去屎上雕花了，索性就自己重头再写一版。

说来也好笑，这还是我第一次用 Go 写一套完整的 Web API 服务，以前要么使用 Go 写中间件或命令行工具，要么是接手别人写好的 web 服务，要么就是用 Python 从头写 Web 服务。不过也不难，只是花了点时间去构建项目结构。也没按照之前 AI 写的设计方案，而是自己重新写的方案。

古法编程的过程中，只让 AI 帮忙生成了 JSON 对应的结构体，以及让 AI 帮忙 review code 和排查错误。以前自己用 ORM 比较多，这次换成用纯 SQL 操作数据库，顺带复习下 SQL 语法。我当初学 Go 语言还是 1.12 版本，笔记也都陈旧了，如今 Go 1.27 都 release 了。虽然 Go 保证兼容旧版本，但用新版本的写法会更方便点。这次古法编程过程中，我一边用新版本来写，一边更新自己的笔记，一边用 AI 对笔记查漏补缺。这个简单的后端服务花了我不少时间，但我也学到了很多东西，也更好地梳理了一遍我的知识体系。

在古法编程时代，大多数时候能把功能做出来就行，很少有开发会一行行 review，早点做出来早点下班才是正事。而在 AI 编程时代，写代码的速度非比以往，随着 AI 能力越来越强，可能以往人们手动写两个函数的工夫，AI 已经把整个需求实现完了。而这时候，比单纯写代码实现功能更重要的，应该就是“知道为什么”和“品味”了。毕竟，“能不能做”和“能不能做好”其实是两回事。虽然只是一字之差，但往往意味着架构调整或大规模代码改动。你可能会说：这也非必要吧，只要写好 `AGENTS.md` 和 skills，AI 也能把代码写得很漂亮。那如果本身没有 know why 和 taste，你怎么知道代码写得好不好呢？

随着 AI 能力越来越强，可能以后人们编程也不需要 know why 和 taste 了，直接全程用 AI 写代码就行。也许以后也不需要太多专门的开发人员了，也许明年我就失业了，也许以后我对编程就不再感兴趣了，但至少现在，当我靠自己做出一个成果的时候，我还是挺开心的。
